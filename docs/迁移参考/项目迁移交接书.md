# 会议时间协调微信小程序：项目迁移交接书

导出日期：2026-11-05。本文用于交给另一个云端开发对话独立接续项目，不依赖原聊天记录或原 Mac 路径。

## 1. 项目目标与用户原始需求

用户希望做一个职场多人会议时间协调工具，称为会议预约“Battle”。发起人提出会议需求，给出一个日期／时间范围和预计会议长度，形成候选时段；参会人进入同一个会议页面，选择自己可以参加的时间；信息共享，后加入的人可以看到先加入的人的选择；系统汇总所有人都能参加的时间，减少群聊中反复询问和人工统计。

核心流程：创建会议需求 → 分享邀请 → 各自填写可用时间 → 共享汇总 → 寻找共同时间 → 发起人确认会议。

产品面向中文职场、手机使用优先，尤其适合不能共享个人日历的跨部门／跨公司协作。重点是可用性协调，不是抢占单个预约名额。

## 2. 用户已明确确认的决定

- 直接以微信小程序作为第一部署平台；用户平时主要在小程序内工作。不要改回“先上线独立网站”路线。
- 使用个人主体。
- 用户最近一次明确反馈：尚未注册小程序账号，也未安装微信开发者工具。该反馈来自此前对话，迁移时需确认是否已有进展，不能当作已实时核实。
- 用户要求实际推进，给出清晰阶段和准备项；能够并行的工作并行，特别是备案等待期间继续设计开发。
- 本轮要迁移到另一个配置了不同环境的云端对话进行搭建。云端对话的工具、系统、运行环境、已有仓库与凭证未知，接手后需先检查。

## 4. 第一版实施基线：此前助手建议，允许优化

以下是为推进工作提出的默认设计，不是用户逐条确认的硬约束。可按真实试用调整，尤其是身份认领、创建人审批、具体数值和界面布局；保持原始目标和已确定的小程序平台。

### 4.1 创建会议

- 输入主题、会议目的、候选日期、每天可安排时间、会议时长、回复截止时间、预期参会名单。
- 标记必到／可选。创建人是否参会独立设置；参会时也要填写可用性。
- 会议时长与候选开始时间间隔独立设置。例如 60 分钟会议、30 分钟开始间隔，可产生 09:00—10:00、09:30—10:30。
- 系统生成完整候选时段，创建人可删选后发布。第一版优先完整时段逐项选择，后续再考虑自由涂抹空闲时间。
- 每个候选必须是连续、完整且不超出范围的会议时段；不能把分散空闲相加当作可用。
- 内部暂称“会合”，不是用户确认的正式名称，也未做命名可用性核验。

### 4.2 邀请、身份与权限

- 分享卡片定位到指定会议，携带必要邀请凭证；知道会议编号本身不等于有权访问。
- 微信身份绑定本人回复；首次填写工作姓名。不假设能自动拿到真实姓名、手机号、公司通讯录或微信群成员。
- 需要预期名单或等效机制，才能准确统计谁未回复。
- 此前建议：成员认领名单身份、创建人确认绑定；待确认者不参与正式汇总。此步骤可优化，避免每次加入都产生过多操作。
- 重名、重复认领不能覆盖他人；同一微信用户反复进入不能重复计数。
- 只有本人可改自己的回复；只有创建人能管理名单、锁定、取消。后台必须验证权限。
- 邀请可撤销；撤销对新加入者和已加入成员的访问影响需在实现中明确，不隐式改变。

### 4.3 填写与共享

- 状态：可以、可协调、不行、未填写。未填写与整个人未回复均不能算可以。
- 可批量操作；不静默把空白转换成不行。
- 默认提交前填完所有候选；全部不行也可明确提交。
- 草稿不参与汇总；显式保存后共享，截止前可以修改自己的回复。
- 默认会议成员可查看已提交的姓名与选择，满足用户要求的公开协调。后续可加仅显示人数模式。
- 不收集私人日程详情或要求解释不方便的原因。
- 更新需在同一个会议共享；可以先用提交后刷新、页面进入刷新或低频更新，不要求每个点击都实时广播。显示最后更新时间，不能让旧数据看起来是最新结果。

### 4.4 推荐与无交集

- 优先全员明确可以；其次必到人员全部明确可以，再按可选人员明确可以人数排序；平局按时间先后。
- 可协调单独显示，不算确定同意。
- 有人未回复时必须显示缺口；不能把“已回复者均可以”说成全员可以。
- 第一版默认只有必到人员全部明确可以才允许锁定。可选人员未回复或不行时展示提示，由创建人判断。
- 必到人员仅可协调时，显示需协商的具体人员，得到明确可用回复后再锁定。
- 没有合格交集时，展示冲突人员，允许复制信息发起新一轮，扩大日期或修改时长；不擅自删掉必到人员、缩短时长或自动选最高票。

### 4.5 截止、锁定与改期

- 状态建议：草稿 → 收集中 → 截止待确认 → 已锁定；另有已取消。无交集是结果状态，不等于自动取消。
- 截止后普通成员不能继续改票；创建人可延长截止重新开放。
- 创建人锁定时服务端读取最新回复并校验版本，正确处理与成员修改同时发生的情况。
- 锁定后停止投票，显示最终时间，支持复制会议通知。第一版不等于自动建视频会议或写入他人日历。
- 已收集回复后，不直接修改候选时段、会议长度或必到要求；实质变更发起新一轮并重新收集。旧回复不能套到新时段。
- 时间存储应有明确时区，第一版默认北京时间；所有人看到同一场会议的同一真实时间。演示数据用相对未来日期，不能依赖旧示例日期。

## 5. 页面结构与体验

| 页面 | 必要内容 | 必须处理的状态 |
|---|---|---|
| 我的会议 | 我发起／我参与、会议状态、入口 | 空列表、加载失败 |
| 创建会议 | 范围、时长、候选、名单、截止、发布 | 无候选、过去时间、重复名单 |
| 加入与填写 | 身份、会议说明、逐项／批量选择、提交修改 | 邀请失效、认领冲突、未填完整、已截止 |
| 协调结果 | 回复进度、未回复者、推荐候选、人员明细 | 无交集、数据变更、无锁定权限 |
| 最终安排 | 时间、名单、地点或链接（可后补）、复制通知、取消／新一轮 | 已取消、改期、旧版本访问 |

手机优先，清晰自然的中文文案，采用“选择可用时间”“查看共同时间”等中性表达。先验证页面结构、关键按钮和异常状态；视觉精修与后端联调并行，不需要等完整高保真稿才能开发。

## 6. 第一版边界

必须完成：创建、邀请、本人填写和修改、共享结果、必到规则、无交集提示、创建人锁定、最终通知、基本身份与权限。

暂缓：自动读取日历、自动创建视频会议、支付、周期排期、企业通讯录、AI 排期、无限自动催办。日历 .ics 导出、订阅消息、隐藏个人明细列入后续，不作为首轮跑通的阻塞项。

先以 3—10 人的一场会议验证；具体人数上限和候选数上限由实现提出，不把演示规模当作产品硬限制。

## 7. 推荐架构与云端接手注意事项

此前推荐：微信原生小程序 + 微信云开发／CloudBase（数据库、云函数、身份能力）。这是技术建议，不是已经开通的环境或必须沿用的既有代码。

- “云端开发对话运行环境”与“小程序线上云后台”是两个不同概念；前者存在不代表后者已部署。
- 先检查当前云端仓库、可用工具、网络和凭证。若目标环境有适用的 AGENTS.md 或技能，按其要求工作。
- 不假设云端装有图形版微信开发者工具；可先完成工程、逻辑验证和可重复构建，再交付用户导入工具真机测试。
- 不依赖原 Mac 的绝对路径、缓存运行时或聊天内可视化宿主。
- 模拟数据层与真实后端分开，明确标识模拟模式。真实 AppID／环境 ID 用配置注入，不伪造可上线的配置。
- 在云端确认微信身份和业务权限；不能信任客户端提交的创建人身份或 OPENID 字符串。
- 并发回复按用户独立存储或以事务处理，避免一个用户保存整张表覆盖其他人；锁定需与回复更新有一致性保证。
- 数据设计可围绕会议、候选时段、成员绑定、回复、邀请、最终安排展开，具体数据库结构由接手实现决定。
- 不需要为交集计算接入大模型。
- 资源用量、实时监听连接数和套餐限制需要重新核对，不继承旧聊天中的报价或承诺。

## 8. 可并行推进的实施计划

| 里程碑 | 开发工作 | 用户／平台工作 | 验收结果 |
|---|---|---|---|
| M0 规则与原型 | 阅读交接、检查环境、完善手机流程 | 注册个人账号，核对服务类目，安装工具 | 流程可演示，个人主体适用性有核查路径 |
| M1 本地模拟 | 建原生工程与模拟数据层，完成全部关键页面 | 确定名称简介，按后台要求认证、备案 | 不接云也能演示一场完整协调 |
| M2 真实联调 | 云函数、数据库、权限、共享更新与锁定 | 提供 AppID／环境 ID，完成必要授权 | 两个真实微信账号可共享且互不覆盖 |
| M3 体验测试 | 处理异常、弱网和交互，修复试用问题 | 添加 3—5 位体验成员，跟进备案 | 真实会议完成，关键验收通过 |
| M4 发布 | 生产配置、隐私说明、审核演示路径、基础监控与备份 | 核对平台手续、审核和发布 | 正式版可用 |

备案与开发尽量并行，前提是名称、主体和服务范围已确定且平台允许进入相应流程。不能保证具体审核周期。此前估算整体开发约 2—4 周，仅供规划，不是已承诺进度；迁移后重新结合环境估时。

个人主体类目是否匹配、认证要求、订阅通知能力需在真实后台核验；不随便选不符功能的类目。若不匹配，应说明具体阻塞与可选调整，继续可做的原型和本地工作。

## 9. 关键验收场景

1. 3 名必到、1 名可选：全部明确可以的候选排在最前。
2. 必到人员尚未回复：不能显示全员可用或允许按满足必到条件锁定。
3. 可协调与不行分开统计；仅可协调不能冒充确定可以。
4. 用户明确提交全部不行：计作已回复，并提示无交集而非未填写。
5. 两人同时保存各自回复：双方信息都保留；退出后再次进入仍在。
6. 修改他人回复、非创建人锁定、失效邀请访问：服务端拒绝。
7. 必到人员修改与创建人锁定同时发生：结果有明确一致性，不锁定过期结果。
8. 截止后不能普通改票；延长截止后可重新填写；锁定后停止投票。
9. 更改长度或候选时间开启新一轮，旧选择不被错误沿用。
10. 同名、重复认领、同微信重进不会重复计数或覆盖他人。
11. 真机弱网、加载失败、保存失败都有可理解提示；失败不能显示已成功保存。

真实多人验收必须使用不同微信账号；单机模拟切换身份不能代替。

## 10. 接手后的第一轮行动

1. 读取本交接与现有仓库，明确哪些是文档、哪些是实际代码。
2. 简短确认当前账号／工具进展；无需重新询问已确定的小程序平台和个人主体。
3. 检查目标环境能力，给出可执行任务拆分与首个里程碑。
4. 没有 AppID 时先推进页面、模拟数据层和纯业务逻辑；有账号再接真实微信云开发。
5. 完成一个可导入微信开发者工具的小程序工程，附导入说明、配置清单、已验证项和未验证项；不要只再输出一份泛泛计划。
6. 若缺少图形工具或账号权限，说明受限的具体验证步骤，继续完成不依赖它们的工作。
