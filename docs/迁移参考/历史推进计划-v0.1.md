# 会议协调小程序：项目推进计划 v0.1

日期：2026-10-28。状态：启动阶段；以下默认规则用于推进原型和开发，可根据试用修改。用户已确认：个人主体；尚无小程序账号，尚未安装微信开发者工具。AppID、云环境与个人主体后台可选类目尚待核实。本文不是已完成部署的说明。

个人主体起步顺序：本人注册账号 → 核对可用服务类目与资质要求 → 完善基础信息、按后台要求办理认证和备案；安装开发者工具可同时进行。个人主体能否使用匹配会议协调功能的类目需以真实后台确认，不预先保证类目或订阅通知能力可用。如不匹配，先保留本地原型，再讨论主体或平台调整，不随意选不符实际功能的类目。

## 1. 第一阶段目标

让一场 3—10 人的真实会议完成：创建需求 → 分享邀请 → 成员填写 → 查看共同时间 → 发起人锁定。

技术路线：微信原生小程序 + 微信云开发。先本地模拟数据，再接云函数和数据库。原型不作为可正式上线的版本。暂用内部代号“会合”，不代表已获准使用该名称。

## 2. 两条工作线与依赖

| 阶段 | 账号与上线准备（用户主导） | 产品与开发（助手推进） | 进入下一阶段的条件 |
|---|---|---|---|
| 启动 | 明确账号持有人、检查已有账号及 AppID、安装开发者工具 | 整理规则、页面流程和验收场景 | 默认规则可用于原型；无需先完成备案 |
| 准备 | 核对后台类目、完善名称简介和图标、按要求认证及提交备案 | 完成手机交互原型、本地模拟流程 | 本地流程可演示 |
| 联调 | 管理员扫码、开通并关联云环境、添加必要成员 | 实现云函数、数据权限、多人同步 | 真实 AppID、可用云环境和开发权限 |
| 体验 | 组织 3—5 位同事加入体验成员，跟进备案补充材料 | 上传体验版本，修复真机问题 | 不同微信账号可完成整场协调 |
| 发布 | 核实备案、认证和类目状态，完成发布操作 | 准备隐私声明、审核路径、版本说明、生产配置 | 功能完整、云环境可用、平台手续满足要求 |

备案办理可与原型、前端开发、后端开发和联调重叠；具体后台入口可用性及材料以前台实际显示为准。小程序备案、主体认证、代码审核是不同事项，不能相互替代。

## 3. 用户现在需要准备的内容

- 账号归属已确认个人；下一步本人在微信公众平台注册小程序账号，核对个人可选类目并取得 AppID。
- 微信公众平台账号与管理员微信；登录、实名、人脸核验、短信核验由本人完成。
- 如使用公司／组织主体，准备对应主体证件及负责人资料，具体按后台清单提交。
- 小程序名称备选 2—3 个、简短介绍、临时图标。正式提交材料时保持名称和服务范围一致。
- 安装微信开发者工具；不必预先购买独立服务器或域名。
- 一场真实但不敏感的样例会议：3—10 人、明确日期范围、时长、必到人员。
- 3—5 位愿意试用的同事。

AppID 和环境 ID 可用于项目配置；无需在聊天里发送 AppSecret、账号密码、证件照片或验证码。

## 4. 第一版需求基线

### 创建与加入

1. 创建人输入会议主题、目的、候选日期、工作时间、会议时长、截止时间和预期名单。
2. 时长与开始时间间隔独立；默认会议 60 分钟、开始间隔 30 分钟。创建人确认一组完整候选时段后发布。
3. 名单中标记必到／可选，创建人是否参会单独确定；参会则同样填写可用性。
4. 分享卡片携带会议标识及邀请凭证，用户打开后进入对应会议。
5. 首次加入填写工作姓名，认领名单身份；创建人确认绑定。待确认身份不进入正式汇总。姓名重复或已被认领时提示联系创建人，不覆盖原绑定。
6. 微信身份用于绑定自己的回复，不自动视为真实工作姓名或群成员名单。邀请凭证可撤销；不能把知道会议编号视为拥有访问权。

### 时间回复

1. 候选时段有“可以／可协调／不行／未填写”四种状态。
2. 初始全部未填写；允许批量设为不行，但不能静默把未填写变成不行。
3. 提交前要求明确填写所有时段；全部不行也可提交。
4. 显式保存后才成为团队可见的已提交回复，草稿不参与汇总。截止前可修改自己的回复。
5. 第一版默认会议成员可查看已提交明细，不显示私人日程或不便原因。后续可增加仅人数模式。
6. 低频刷新或受配额约束的实时监听均可；显示最后更新时间。后台身份、权限和汇总不能依赖客户端传入的角色字段。

### 推荐与锁定

1. 全员明确可以优先；其次必到全部明确可以，按可选人员明确可以人数排序；同条件按时间先后。
2. 可协调不计作明确可以；存在未回复时显示进度，不能标为全员可用。
3. 第一版仅在所有必到人员对选定时段明确可以时允许锁定。可选人员未回复／不行时显式提示，创建人仍可确认。
4. 没有合格候选时段，展示差在哪些人，并提供新建一轮协调、复制原有信息的入口。新一轮重新收集回复。
5. 发布后不直接改变原候选时段、时长和人员要求；实质调整通过新一轮协调处理，避免旧回复被套用。
6. 截止后停止普通成员修改，会议进入待确认。创建人可延长截止时间重新开放；不会自动选一个结果。
7. 锁定在服务端校验最新回复和版本；与回复修改冲突时重新读取，不能依据旧页面强行锁定。
8. 锁定后停止投票，显示最终安排、复制通知文案；改期另起一轮。仅创建人可锁定或取消。

暂不包含：自动读取个人日历、自动创建视频会议、支付、周期排期、通讯录同步、无条件自动催办、AI 推荐。订阅通知及日历导出不作为第一场会议跑通的前置条件。

## 5. 页面与交互任务

| 页面 | 主要信息与操作 | 首批必须呈现的异常状态 |
|---|---|---|
| 我的会议 | 我发起／我参与，收集中／待确认／已锁定／已取消 | 无会议、加载失败 |
| 创建会议 | 会议目的、候选时间、名单、必到标记、截止 | 无候选时段、时间过期、名单重复 |
| 加入与填写 | 工作姓名与身份确认、完整时段选择、提交／修改 | 邀请失效、身份待确认、未填完整、已截止 |
| 协调结果 | 回复进度、未回复名单、候选排名、人员明细 | 无交集、信息刚被更新、无锁定权限 |
| 最终安排 | 已选时间、会议状态、通知文案、取消或新一轮 | 已取消、已被其他操作锁定 |

设计先做页面结构、关键按钮、状态文案和手机点击路径；视觉精修与后端联调并行。先验收能不能完成任务，再调整配色、图标和留白。

## 6. 里程碑与验收

时间为熟悉开发情况下的估算，按启动后的工作日计算；手续等待不计入开发承诺。

- M0（第 1—2 天）：需求基线与手机原型。用一场样例会议演示所有关键状态。
- M1（第 3—5 天）：本地模拟版本。创建、填写、汇总、锁定流程可操作；数据为本地模拟，不能声称多人同步。
- M2（第 6—10 天）：云端联调版本。至少两个真实微信账号能加入同一会议、各自修改且互不覆盖；重进页面数据保留。
- M3（第 11—15 天）：体验版本。3—5 人真实试用，覆盖未回复、全不行、无交集、截止和改期。
- M4（约第 3—4 周起）：上线准备。修复体验问题、核对手续、提交完整版本审核；正式发布日期依后台审批结果决定。

云联调验收必须覆盖：越权修改被拒绝、并发回复不丢失、必到人员不能遗漏、未回复不能算同意、锁定与修改竞争时结果一致、邀请失效不可继续访问。

上线基本验收还包括：弱网与失败提示、敏感信息最少收集、数据库权限、错误记录、资源告警、数据备份、生产环境与测试数据隔离、审核人员可完整体验的测试路径。
